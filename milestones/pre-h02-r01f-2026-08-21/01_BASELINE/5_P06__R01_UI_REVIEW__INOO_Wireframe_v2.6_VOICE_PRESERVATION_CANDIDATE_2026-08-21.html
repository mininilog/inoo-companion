5 · Staging → 새 forward revision 후보
승인 후에도 기존 verified canonical 상태를 유지한 채 transaction/staging 영역에서 복원 payload를 새 revision 후보로 구성한다. 기존 HEAD를 단순 overwrite하거나 뒤로 이동시키지 않으며 partial apply를 허용하지 않는다.
6 · Read-back verification → 성공 시에만 확정
staged candidate를 다시 읽어 구조·해시·scope를 검증하고 모든 검사가 성공한 경우에만 새 canonical revision으로 확정한다.
FAIL CLOSED · 파싱/무결성/schema/version/migration/read-back 중 하나라도 실패하면 새 후보를 확정하지 않는다. 기존 verified canonical state는 100% 유지하고 읽을 수 있는 Recovery / Raw Recovery Export 경로를 계속 보존한다.
Remote notice/update는 안내만 할 수 있고 Restore mutation authority가 아니다. 로컬 결정적 검증 + 사용자 명시 승인이 복원 적용의 필수 gate다.
Forward Rollback · 과거 상태를 새 revision으로 복구P-04-2
단일 경로: [관리] → [Data Safety] → [Forward Rollback]. 과거 revision의 상태를 source로 사용할 뿐 현재 HEAD를 과거로 이동시키지 않는다. Replica Transfer/Conflict는 P-04-3 범위이므로 여기서 처리하지 않는다.
1 · 복구 대상 revision 선택
Rollback target · 날짜는 식별 보조 정보이며 실제 authority는 revision_id
2 · 대상 revision 검사
선택한 revision_id가 존재하고 읽을 수 있으며 verified history에 속하는지, 필요한 snapshot/lineage metadata를 안전하게 재구성할 수 있는지 검사한다. 검사 실패만으로 현재 canonical state를 변경하지 않는다.
3 · Forward Rollback Preview
롤백 후 변화 미리보기검사 후 표시
현재 verified HEAD현재 revision_id · 성공 검증 전까지 authority 유지
선택한 대상rollback_target revision_id · 생성 시각은 보조 표시
변경될 상태현재 HEAD와 선택 대상 간 Canonical USER_STATE / 승인된 portable state 차이
새 revision 계획과거 revision payload를 source로 새 forward revision candidate 생성

4 · 사용자 명시 승인
검사 PASS와 Preview 확인 전에는 실행 버튼을 활성화하지 않는다. 사용자의 명시 승인 없이 canonical mutation 금지.
5 · 새 forward revision candidate 생성
현재 verified HEAD/state를 그대로 보존한 staging/transaction에서 선택한 과거 상태를 복사해 새 revision 후보를 만든다. 새 후보는 현재 HEAD의 다음 계보에 추가되며 rollback_target 및 lineage metadata를 보존한다.
6 · Read-back verification → 성공 시에만 새 HEAD 확정
새 candidate를 다시 읽어 payload · metadata · lineage · rollback_target · expected scope를 검증하고 모두 일치할 때만 해당 새 revision을 canonical HEAD로 확정한다.
FAIL CLOSED · 대상 읽기/Preview/staging/metadata/read-back 중 하나라도 실패하면 새 revision을 확정하지 않는다. 기존 verified HEAD와 canonical state는 100% 유지한다.
P-04-2는 과거 상태를 복사해 앞으로 새 revision을 만드는 경로다. Conflict 판단·자동 merge·incoming replica 선택은 하지 않는다.
Replica Conflict · 충돌 분기 직접 선택P-04-3
단일 경로: [관리] → [Data Safety] → [Conflict]. 서로 다른 저장 컨테이너의 lineage가 갈라진 CONFLICT만 다룬다. iPhone/Android는 예시이며 replica_id는 물리 기기가 아니라 저장 컨테이너 식별자다.
1 · CONFLICT 감지 · 자동 overwrite 차단
Current Local과 Incoming Replica의 lineage / HEAD / replica_id가 일치하지 않으면 충돌 상태로 분류한다. 최신 날짜, 더 큰 revision 번호, 더 새로 보이는 기기라는 이유만으로 어느 쪽도 자동 선택·overwrite하지 않는다.
